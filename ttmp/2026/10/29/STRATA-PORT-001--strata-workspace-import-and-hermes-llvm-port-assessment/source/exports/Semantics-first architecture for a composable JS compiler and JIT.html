Semantics-first architecture for a composable JS compiler and JIT

2026-10-29 · @u_1uYef92nx3NfIGSZsVBDYg

Summary

Build the compiler around one executable specification and three composition laws. Everything else is a replaceable part with a written contract.

The goal is a JavaScript-to-native compiler and JIT that stays simple as it grows. It should reuse Hermes and LLVM today, and let any part later be swapped for our own component without losing correctness.

The design in five points:

  • Meaning is defined by a reference interpreter over a small core IR. It is the specification, the test oracle and the place to fall back to.

  • JavaScript behaviour enters only as operations with contracts. Hermes implements them today; our own runtime can implement them later, one operation set at a time.

  • Composition follows three laws. Passes refine their input, so a pipeline of correct passes is correct. Analyses are monotone, so one solver serves all of them. Components satisfy contracts, so replacements stay local.

  • Physical choices (value representation, GC roots, exception transfer, code materialization) are strategies that must meet stated safety invariants.

  • Execution ownership (engine, code, activations, modules, jobs) is a set of state machines outside the compiler.

Relation to LLVM-ENGINE-002: doc 01 covers execution ownership (layer 6 here). Doc 02 is a first draft of layers 2 to 5. Doc 03 is the research method. This note is the positive thesis the seminar should test, and may reject.

Everything here is proposed; nothing is implemented. A companion artifact sketches a JavaScript builder API over this design.

Principles and the simplicity test

"Simple" here means few concepts that compose by law, not few lines of code. Seven principles, each tied to a decision:

  1. Meaning first. Every component is judged against the reference semantics. A builder, IR or pass has no meaning of its own.

  2. Small core, open edges. The core IR knows values, blocks, branches and continuations. JavaScript lives in operation sets that plug into it.

  3. One fact, one place. "May trigger GC" or "may run user code" is declared once, in an operation's contract. Analyses derive from it; emitters never restate it.

  4. Compose only by law. A part plugs in only where a law says the whole stays correct: refinement, monotonicity or contract satisfaction.

  5. Pluggable exactly where a contract exists. Each plug point names its contract and how a replacement is checked. Anywhere else, extension hooks are just indirection.

  6. Conservative unless proven. Unknown behaviour means "may do anything". Precision comes from facts with an origin (a guard, a type, an analysis), and a fact is dropped when its origin changes.

  7. Inspectable at every boundary. Each level dumps as text and JSON with provenance. Diagnostics are structured data.

The simplicity test, applied to every proposed change:

ChangePasses whenFails when
New JS featureIt adds operations with contracts and lowering rulesIt adds a core IR construct or special cases in passes
New optimizationIt is a rewrite whose side condition reads permissions and factsIt needs a new node kind or hidden knowledge of helpers
New analysisIt supplies a lattice and transfer functionsIt needs its own iteration engine
Replacing a runtime pieceIt re-implements an operation set against the same contractsCallers must change
New root or exception policyIt is a strategy checked against the same invariantsSemantic passes must know about it

Expressiveness is measured against doc 03's five comparison examples and doc 02's 26-example ladder. A design that makes arithmetic elegant but obscures captured cells, throwing getters or job order fails.

The spine at a glance

Seven layers carry the design. Layers 2, 3, 5 and 7 appear as pipeline levels below; layer 4 (analyses) runs between them; layer 6 (the engine) receives the result; layer 1 (the specification) checks every level.

Read it top down: each level refines the one above it, each plug point on the right is swappable under its contract, and the dashed lines are the checks against the reference interpreter.

Layer 1: the reference interpreter is the specification

The specification is a small-step interpreter over the core IR, plus a reference step for each operation. It answers one question: what may this program observably do?

The machine state follows doc 03's starting hypothesis:

state   = (block, env, heap, continuation, jobs, trace)
state --label--> state'
label   ::= silent | output(v) | host_call(name, args) | settle(job, outcome)
outcome ::= normal(v) | throw(v) | diverge

Observations are explicit, not "printed text". A behaviour is a trace of labels plus a final outcome. Two behaviours are equal up to a renaming of heap locations that preserves identity and aliasing. Numbers compare with SameValue, so NaN and signed zero are exact. Running out of a resource (an admission limit, memory) belongs to a separate resource profile, so a storage change cannot pass for a semantic change.

The interpreter has three jobs:

  • Specification. Each operation set supplies reference steps; the core supplies blocks, branches and continuations.

  • Oracle. Every level can be compared against it on small programs, independently of Hermes.

  • Fallback tier. It is where execution resumes after a failed speculation (see the JIT section), and a candidate executor for dynamic eval code.

Language profiles name what is admitted, and every correctness claim is a claim for a profile:

ProfileAdmitsPreserved observations
coreNumbers, booleans, control flow, closures, mutable cellsOutput, outcome
js-syncObjects, prototypes, coercions, getters, exceptionsPlus identity, heap mutation, thrown values
js-asyncPromises, jobs, generators, async functionsPlus job order
js-modulesLinking, live bindings, top-level awaitPlus evaluation order, pending vs settled
js-dynamicDirect and indirect eval, FunctionPlus shared binding cells

The interpreter is not a second JavaScript engine. For operations we don't own, it delegates to Hermes as a declared provider. It implements only the core and the operation sets we choose to own.

Layer 2: core IR with block parameters and explicit continuations

The core IR is an SSA control-flow graph whose blocks take parameters. That form is first-order functional code in disguise (Appel; Kelsey's CPS/SSA correspondence), so its meaning is simple to state.

Its constructs, and nothing else:

ConstructMeaning
FunctionParameters, entry block, declared result and exception types
BlockParameters, a list of operations, exactly one terminator
OperationNamed by an operation set; operands, results, attributes
invokeAn operation with a normal successor and an exceptional successor
Terminatorsjump, branch, return, throw, unreachable
Region (optional)A nested body for closures and structured constructs before lowering

One verifier checks five well-formedness rules:

  1. Each value has one definition, and that definition dominates every use.

  2. Each edge passes exactly the arguments its target declares, with matching types.

  3. An operation that may throw appears only as invoke, or in a block with a declared exceptional exit.

  4. An exceptional successor receives the thrown value and the state after effects already performed. Nothing rolls back.

  5. Every block ends in exactly one terminator. Unreachable blocks are reported, not silently dropped.

What stays out of the core:

  • JavaScript coercions, property access, allocation, closures, generators and modules. These are operation sets (Layer 3).

  • GC roots, slots, activation layout and setjmp. These are lowering strategies (Layer 5).

  • Native addresses and engine handles. These belong to the engine (Layer 6).

Effect ordering is an open choice the seminar should settle by comparison (doc 03 §3.3). Option A threads explicit state tokens through effectful operations, as doc 02 proposes. Option B keeps operations ordered within blocks and consults contracts before moving them, as MLIR does. This note leans to B for the stored IR, with tokens available as a derived analysis view, because it keeps the IR smaller. That is a lean, not a decision.

Layer 3: operations with contracts are the main plug boundary

An operation set is a named, versioned group of operations, each with a contract. The contract is the only place an operation's behaviour is declared to the rest of the compiler.

A contract has halves that answer different questions (doc 03 §3.2):

contract(op):
  signature      operand and result types, attributes
  semantics      reference step function, used by the interpreter
  behaviour      reads, writes (by resource), fresh identity, may throw,
                 may diverge, may run user code
  permissions    derived: may it be erased, duplicated, moved, hoisted,
                 speculated?
  obligations    what lowering must guarantee: may collect, borrowed
                 operands, result protection, nonlocal transfer,
                 write barrier, host capability
  variants       cheaper operations valid under stated facts

Permissions are derived, never asserted. can_erase(op, facts) holds only if the operation cannot throw, cannot diverge, writes nothing observable, and its fresh identity is unobserved. An unused result alone is not enough.

OperationPermissionsObligationsNote
num.add(f64, f64)Erase, move, duplicate, speculateNoneNo reassociation: floating point
js.add(v, v)None in generalMay collect, may throwMay run user code via valueOf; facts narrow it
js.get(obj, key)None in generalMay collect, may throwGetter or proxy; a known data property narrows it
obj.new()Erase if identity unobserved; never merge twoMay collectFresh identity
job.enqueue(fn)Never reorder with other enqueuesMay collectWrites the jobs ordering resource
cell.load(c)Move across operations that don't write cellsNoneShared with eval when the binding escapes

Narrowing is where expressiveness meets performance. A fact (from a guard or a type analysis) selects a more permissive variant, for example js.add to num.add when both operands are numbers. The variant's contract must refine the general one whenever the fact holds.

Operation sets planned at first:

Each set has one provider at a time. Hermes provides all of them first.

Composition laws

Three laws make "composable" mean that correct parts give a correct whole. Each can be checked without a full proof.

Law 1: refinement composes. Write P ⊑ Q when every behaviour of P is allowed by Q, within a profile. A pass p is correct when p(Q) ⊑ Q. Refinement is transitive, so a pipeline of correct passes is correct end to end. This is CompCert's structure.

p_2(p_1(Q)) \sqsubseteq p_1(Q) \;\wedge\; p_1(Q) \sqsubseteq Q \;\Longrightarrow\; p_2(p_1(Q)) \sqsubseteq Q

Refinement rather than equivalence, because lowering may legitimately narrow nondeterminism, for example the order of independent timers. Where two-way equivalence matters, the profile says so.

Law 2: contracts compose. A component that satisfies the contracts of the operations it implements can replace any other that does. Callers see only contracts. A contract is checked by verifier rules, by property tests against the reference steps, and by differential runs against the previous provider.

Law 3: monotone analyses compose. A product of lattices is a lattice, and a tuple of monotone transfer functions is monotone. Analyses can therefore run together in one solver, with termination guaranteed on finite-height domains.

Each level boundary gets a check, chosen by cost:

BoundaryStructural checkSemantic check
Source to core IRVerifier rules 1–5Interpreter vs Hermes on test sources
Core IR to runtime IREvery operation bound to a provider; no unknown operation survivesTranslation validation on small functions
Runtime IR to execution planGC-safety and unwind invariantsForced GC at every collecting point in tests
Plan to native artifactLLVM verifier plus descriptor checkDifferential execution against the interpreter
Artifact to engineABI, target and version matchLifecycle tests: failure, reentry, close

Smaller algebraic laws are tested as properties: effect summaries join associatively, commutatively and idempotently; canonicalization is idempotent; serialization round-trips exactly, including BigInt bytes and UTF-16 strings. A passing property test is evidence, not proof. Every counterexample is kept as a minimized fixture.

Layer 4: one analysis substrate of lattices and fixed points

Every analysis is a lattice, a direction and a transfer function per operation. One worklist solver computes the least fixed point. This replaces analysis logic now spread through the emitter.

analysis A:
  lattice     (L, ⊑, ⊔, ⊥), finite height or with a widening operator
  direction   forward | backward
  transfer    op -> (L -> L), monotone
  edge        how facts cross an edge: block-argument substitution,
              exceptional edges
solve(A, cfg) -> facts at every program point
AnalysisLatticeDirectionConsumer
LivenessSets of valuesBackwardRoot planning, slot reuse
Effect summaryRead/write sets per resource, plus flagsForwardRewrite permissions
Type factsPer value: ⊥, int32, number, string, object, …, anyForwardOperation narrowing
EscapePer allocation: local, captured, escapedForwardAllocation removal
SafepointsPer point: may collectForwardRoot planning
Definite initializationPer binding: uninitialized, initialized, unknownForwardRemoving TDZ checks

Two rules keep the solver honest:

  • Edges are part of the analysis. Edge transfer must substitute block arguments and include exceptional edges. Liveness without them drops required roots.

  • No iteration caps. Termination comes from finite height or explicit widening. Running out of budget is a diagnostic or a sound conservative fallback, never a silently partial result.

The solver imports nothing from Hermes or LLVM. It is the first candidate reusable subsystem (doc 03 §6), with module-graph reachability and workflow analysis as its second consumers.

Layer 5: lowering strategies and their safety invariants

Lowering turns runtime IR into an execution plan by choosing physical strategies. Each strategy slot is a plug point because each has a written invariant.

Strategy slotOptionsInvariant every option must meet
Value representationHermes NaN-boxed values; unboxed f64 or int32 where facts allowBoxing back to a tagged value is exact
GC rootsNative-stack slots with liveness reuse; runtime-owned activation arena; LLVM statepointsEvery managed value needed after a collecting point is reachable, and later uses see its post-collection value
Exception transfersetjmp/longjmp (current); status returns; LLVM landing padsThe handler gets the thrown value and post-effect heap; abandoned roots and frames are restored together
SuspensionHermes generator lowering (current); explicit continuation objectsNo suspended state points into a released activation
CallsCurrent Static Hermes native ABI; a new engine-local ABICallee sees receiver, arguments, environment and new.target; the result is protected before the frame is released

Strategies combine only in checked pairs. Root storage and exception transfer interact: longjmp skips C++ destructors, so an arena must be rewound by the same checkpoint that restores the root chain. A combination is a named, verified pair, not a free cross-product.

The plan is checked, not trusted. A root plan is valid when every live managed value at every collecting point has a root, and no two values live at the same time share a slot. The checker reads liveness and safepoint facts from Layer 4.

The fflate case is a test of this layer, not a design driver. Its unoptimized module factory asks for 1,084 slots against a 1,024-slot cap, because today every IR value gets its own slot. Under this design the same program should report its peak live values, the chosen root strategy and the resulting budget. Switching strategy must not change any semantic pass.

Layer 6: execution ownership lives outside the compiler

The engine owns everything that exists while code runs; the compiler owns nothing that outlives a compile request. Doc 01's central rule stays: one Engine owns one execution domain.

Each owned thing is an explicit state machine with failure transitions:

Code:        compiled -> admitted -> retained -> released at close
Activation:  entered -> running -> returned | unwound
Module:      registered -> linking -> linked | link-error
Evaluation:  not-started -> evaluating -> pending -> fulfilled | rejected
Job:         queued -> running -> settled
Engine:      ready -> executing -> ready ... -> closed

Contracts carried over from doc 01 and the current code:

  • Admitted code is retained until engine close, because an initializer can publish a closure and then throw.

  • The engine destroys the runtime before releasing executable memory.

  • Pending is not completion: an empty job queue does not fulfil a module evaluation.

  • One registry per engine, so two separately compiled bundles share module records.

  • Code, module, evaluation and handle identifiers are engine-local and opaque.

Generic parts and JavaScript policy stay separate here too. SCC decomposition of the module graph is reusable; linking rules, live bindings and top-level await are JavaScript policy layered on top.

Layer 7: materialization and artifacts

A materializer turns an execution plan into executable code. LLVM ORC (in-process JIT) and LLVM ahead-of-time compilation are two materializers behind one artifact contract.

An artifact carries a target and ABI identity, immutable function descriptors, constants (exact BigInt bytes, UTF-16 strings), source metadata and module declarations. It never carries live managed pointers, engine-local identifiers or process-global unit indices.

Admission is a check, not a cast. The engine rejects an artifact whose ABI version, target or required strategies (roots, exceptions) differ from its own, before any native code runs.

Textual LLVM IR stays the boundary at first. Hermes builds against its own LLVM copy (llvh), and text avoids mixing the two type systems. Switching to in-memory IR is an optimization to make only after measuring parse cost.

A future custom backend (doc 03 stage F) is one more materializer. It must accept the same execution plan and pass the same admission and differential checks.

The JIT question: tiers, speculation and deoptimization

Today's JIT compiles in-process without speculation, while a fast JavaScript JIT speculates on types and falls back when a guess fails. Whether that is in scope decides what the foundations must include now.

GoalWhat the JIT doesWhat the foundations need
In-process compilationCompiles eagerly at load time, as AOT doesNothing beyond layers 1–7
Adaptive tiersInterprets, profiles, compiles hot code on speculated types, deoptimizes when a guess failsAssumptions as facts, guards, frame-state maps, a resume target

If adaptive tiers may come later, three choices should be made now, because they are hard to retrofit:

  1. Assumptions are facts with an origin, in the same fact system as types. A guard produces a fact; a failed guard is an exceptional edge to a deoptimization exit.

  2. Every deoptimization exit carries a frame-state map: how to rebuild the reference interpreter's state (block, environment, live values) from the native frame.

  3. The reference interpreter is the resume target. Deoptimizing means continuing in the specification. Correctness then reduces to one obligation: the frame-state map preserves refinement.

Speculative code refines the general code only on paths where its guards hold, and the fallback covers the rest. That keeps speculation inside Law 1 instead of beside it.

Until then the guides' deferral stands: no speculation, deoptimization or tiering. What this note asks is that the core IR, the fact system and the interpreter do not rule them out.

Doc 03's stages A–F become concrete steps, each useful alone, none requiring the next:

  1. A. Semantic core. Write the interpreter and verifier for core. Hermes stays the reference for everything else.

  2. B. Frontend boundary. Import Hermes IR into the core IR at a chosen pipeline point. Later, optionally, our own parser.

  3. C. Analyses and lowering. The solver, contracts and strategies replace the emitter's implicit decisions. LLVM and the Hermes heap stay.

  4. D. Execution ownership. Engine state machines replace per-bundle registries and process-global unit indices.

  5. E. Managed runtime. Re-implement operation sets one at a time (values, then objects, then functions), each against its contracts, with Hermes as the oracle. A collector comes last.

  6. F. Backend, optional. Only when a measured benefit outweighs the maintenance.

A deciding experiment: encode doc 03's five comparison examples in each candidate. Count added constructs, verifier rules and glue code for the throwing getter and the job enqueue. The cheapest candidate that expresses all five without opaque escapes wins.

A hybrid is plausible: a small custom semantic core and analysis layer, with MLIR or plain LLVM below the execution plan. This note does not presume the answer.

Worked example: the throwing getter through every layer

Doc 03's example shows each layer's job and the optimization the contracts forbid. All traces below are derived by hand, not executed.

let cell = {n: 0};
const receiver = { get x() { cell.n += 1; throw cell; } };
try { receiver.x; } catch (caught) { print(caught === cell, cell.n); }
// Intended observation: true 1

Core IR (Layer 2), using operations from js.object and core (the getter body is a separate function, and the captured binding is simplified to a value):

entry():
  cell     = obj.literal({n: 0})
  receiver = obj.literal({get x: getter_x}, captures=[cell])
  invoke js.get(receiver, "x")    normal done()     throw caught(thrown)
done():
  return undefined
caught(thrown):
  same = ref.eq(cell, thrown)
  invoke js.get(cell, "n")        normal out(n)     throw propagate(e)
out(n):
  host.print(same, n)
  return undefined
propagate(e):
  throw e

Contracts (Layer 3). js.get on an unknown receiver may run user code, write any reachable object, throw and collect. It can be neither erased nor moved, although its result is unused.

Semantics (Layer 1). The getter sets cell.n to 1 and throws cell. The exceptional edge carries the post-effect heap, so caught sees n == 1 and the same identity. The observation is output(true, 1).

Analyses (Layer 4). Liveness: cell is live across the first js.get because caught uses it; receiver is dead after it. Safepoints: both js.get calls may collect.

Lowering (Layer 5). The root plan must root cell across the first call; receiver needs a root only up to it. With setjmp transfer, the handler's checkpoint must restore the root chain so that cell and thrown both survive.

The forbidden optimization. Dead-result elimination deletes js.get(receiver, "x") because its result is unused:

original:   output(true, 1)
optimized:  no output, because the catch block never runs

The rewrite's side condition can_erase(js.get, facts) is false, because the contract says "may throw" and "may run user code". The counterexample becomes the regression test for that rule.

Variants doc 03 asks for:

  • The getter returns normally. The permissions don't change; only the runtime path does.

  • The getter loops forever. "May diverge" alone forbids erasure, even with no writes.

  • The getter enqueues a job, then throws. It writes the jobs resource, so the access cannot move across other enqueues.

Open questions and what would overturn this design

Open questions, each with the experiment that settles it:

  • Ordered blocks or state tokens? Encode the five comparison examples both ways (doc 03 §3.3).

  • Where is the frontend boundary? Importing Hermes IR after some passes may lose binding or source facts that lexical eval needs. Trace eval metadata through eval_extensions.cpp.

  • Can the interpreter stay affordable? If writing reference steps costs as much as the runtime, the specification will drift. Mitigation: write steps only for sets we plan to own, and delegate the rest to Hermes as a declared oracle.

  • Do contracts stay useful? If most JavaScript operations end up as "may do anything", the IR enables little optimization. Precision must come from narrowing by facts, not from optimistic contracts.

  • Can MLIR host the exception and GC protocol? If it can with modest glue, a custom graph library is not justified.

  • Is adaptive tiering a goal? The answer changes what the fact system and interpreter must support now.

Three findings would overturn the design:

  1. Two individually correct passes compose into an incorrect pipeline. The refinement relation or the observations would then be wrong.

  2. A real JavaScript feature cannot be expressed as an operation set without changing the core IR.

  3. A replacement passes every contract check yet changes application behaviour. Contracts would then be too weak to serve as the plug boundary.
